### Locked Decisions (from `106.1-CONTEXT.md`, the ones that govern this phase)

- **D-01/D-02:** the frontier skill is wired only after the Phase 106 rename; the follow-up phase wires it and proves the team run and the headless run.
- **D-05:** two ways to create the record, same result: the launcher `ailsa run start <dataset>` (headless and benchmark runs), and, for a run started by a slash command in an open session, creating the record is the skill's first step.
- **D-06:** run folder name = UTC start time + dataset folder name + short random part; in blind mode only the dataset folder name the agents see anyway.
- **D-07:** a tool called during a run that cannot find its run works normally and warns "not recorded: no active run" on stderr; a run never aborts over bookkeeping; `ailsa run finalize` refuses without a run, so a skipped init cannot end in a silent success.
- **D-08:** agents write in the run's `agent/` working subfolder (shown as "unverified"); nothing is blocked.
- **D-09:** a broken hash chain is shown from the break onward; the run never counts as clean.
- **D-10:** prose progress notes go through the note command (`ailsa run note "..."`): sender and UTC time are added automatically, the note becomes an event. The progress log (`CASE-PROGRESS.md` or its successor) is rendered from tool events plus notes and never edited by hand. Agents can still read the rendered log (loop detection). "For the frontier skill in the follow-up phase."
- **D-11:** the old web view (`ailsa webview`, `src/ailsa/webview/`, auto-launched by the frontier skill) is removed in the follow-up phase together with the frontier wiring.
- `final_results.md` becomes a rendering of the `finalize` declaration plus the tool-written ranking (REC-22); narrative assessment goes into the declaration's confidence / caveats / open questions / next steps fields (REC-16).
- A run without a valid declaration, or whose ranking was hand-formatted, ends "stopped before a result (inferred)"; `finalize` refuses a missing, invalid or stale ranking but accepts outcomes without a chosen candidate.
- SPEC D1 (structured record, strict for the final result), D4 (one workspace folder per run outside the data), D5, D15 (tool steps and the final declaration first), D16 (raw transcripts leave the machine only on explicit request).

## Summary

The package half is finished and verified (106.1): `ailsa run init|note|finalize|close|render|verify|start|hooks`, a launcher, Claude Code hooks, hash-chained event log, typed rankings, strict `finalize`. The frontier skill, by contrast, still works in the old world: its coordinator writes `CASE-PROGRESS.md` as sole author, the agents write into `<dataset>/analysis/`, the coordinator stamps `analysis/timing.jsonl`, writes `analysis/.run_manifest.json` and auto-launches `ailsa webview serve`. About 20 of the 29 skill files carry such paths (change map, section 1). Wiring it means three moves: (1) the agents' working folder becomes the run's `agent/` folder (`WORK`, printed by `ailsa run init`), so the dataset is never written (REC-05); (2) the coordinator's prose log becomes `ailsa run note` lines, its loop-detection reads the rendered log, and the result is declared once with `ailsa run finalize` by the coordinator after both gates; (3) the web view, the timing step and the manifest-writing step disappear. `case.md` has 492 lines of a 500 limit, but the web-view block (about 44 lines) and the timing step leave, so the net change is negative.

Three findings change the plan's shape. **First**, the benchmark runner (`tests/case-benchmark/blind_case_run.sh`) and every grader and the watchdog key on `<dataset>/analysis/final_results.md` and on that file as the stop condition of the resume loop; once agents work in the run folder this file never appears, so the runner must change in the same phase (recommended: put it on the launcher, extended with `--skill ailsa` and resume attempts, and have the runner copy the rendering to the old results path so graders and the watchdog stay unchanged). **Second**, "team run" on the current Claude Code is not what the skill text assumes: the public example run of 2026-11-24 was an interactive session in which `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` was empty, `TeamCreate` was not available (only `SendMessage` was found), and the four specialists ran as named background subagents in one session. With the flag set, Claude Code documents that a named `Agent` call launches a *teammate* instead (a separate Claude Code instance, in-process by default). Whether hooks, the session id and the run lookup behave the same for real teammates is unproven (the 106.1 spike used ordinary subagents), so the proof run on Sheldon doubles as the experiment. **Third**, REC-25 "per agent" is mostly there, but the three evidence sources key agents differently (hex agent id, agent type, free-text sender name) and the hook records `name` of a teammate nowhere, so a small package change is needed to make each agent's model and messages attributable.

**Primary recommendation:** Wire the skill in four plans: (a) package gaps (agent attribution, skill version/installed-hash for the command skill, launcher `--skill ailsa` with resume attempts); (b) skill text rewrite on the `WORK`-folder / notes / finalize model with the web-view and timing removal, guard files and contract tests in the same commits; (c) web-view removal (code, tests, extra, docs); (d) runner on the launcher plus proof runs on Sheldon (interactive team run via tmux, headless run via launcher), with the owner checkpoint on the team run.

### Pattern 1: first step, idempotent, recoverable after compaction

**What:** `ailsa run init <dataset> --formula F --skill ailsa --mode team` right after the prerequisite checks; it prints `RUN:` and `WORK:`. Calling it again in the same session prints the same folders, so it is also the recovery after a context compaction (the status command prints no folder path).
**Evidence:** `docs/RUN-RECORD.md` "Starting a run"; `status_cmd` data keys contain `run_id` but no folder (`src/ailsa/cli/run.py:239-253`); `_result` carries `run_dir`, `work_dir` (`src/ailsa/record/runinit.py:75-85`); launcher branch of `init_run` returns the existing run when `AILSA_RUN_DIR` is set (`runinit.py` "1. Launcher"). Session id is unchanged by compaction [VERIFIED: 106.1-02 SUMMARY].

### Pattern 2: one declarant, explicit ranking id

The solution analyst runs `ailsa lsd rank --assigned ...` (decisive) and then the nearest-line cross-check. Both write rankings; the cross-check is the *latest* (`resolve_ranking` returns `computed[-1]` for `latest`, `src/ailsa/record/finalize.py:73-78`; the JSON output carries `ranking_id`, `src/ailsa/cli/lsd.py:659-660`). So `[RANKING-COMPLETE]` must name the id of the atom-by-atom ranking (`rkNN`) and the coordinator finalizes with `--ranking rkNN`, never `latest`.

**Outcome mapping for every exit path** (all accepted by `finalize`, outcomes from `docs/RUN-RECORD.md`):

| Path in `case.md` | Declaration |
|---|---|
| ranking accepted, name gate passed | `proposal` (or `proposal_under_determined` when the analyst's confidence is low or ambiguity remains), `--candidate N --confidence ...`, caveats / open questions / next steps from the analyst's message |
| ranking done but no candidate trusted | `inconclusive --ranking rkNN` |
| escalation after 10 failed interventions | `handed_to_human` (needs no ranking) |
| zero solutions after every diagnosis | `no_structure_fits` |
| spectra unusable | `insufficient_data` |
| smoke-test mode | `ailsa run close --reason "smoke test"` (no declaration; the record then reads "stopped before a result (inferred)", acceptable and honest) |
| any failure after init (prerequisites, spawn) | `ailsa run close --reason "..."` |

### Pattern 3: progress as notes, loop detection from the rendering

The coordinator writes one compact note per validated structured message, with the fields loop detection reads as `key: value` lines (the list at `references/progress-format.md:210-226`: solution count, constraints added, sp2 count, H budget, HMBC used X/Y, fragment search, fragment file), `--sender <agent> --phase <task>`. `ailsa run note` text cap is 4 000 characters (`TEXT_CAP`, `src/ailsa/record/events.py:29`). Solver counts come for free: the renderer prints "Solver round N: X possible structures (outcome)" from tool events (`render.py` `DIARY_TEMPLATES`). Before each loop-detection pass the coordinator runs `ailsa run render` and reads `renderings/CASE-PROGRESS.md`. The multiplicity coverage ledger becomes notes with `--phase coverage`; the coverage gate reads it from the rendering. Setup detail is too long for one note and already lives in the agents' messages (captured by hooks up to 4 000 characters each) and in the agent's own files in `WORK`; the coordinator notes a summary plus the shift list line.

### Anti-Patterns to Avoid

- **Relative paths in agent Bash calls.** Subagents start in the session's original folder, which for a slash start is the dataset folder; a redirect there writes into the dataset. Every path in spawn prompts, `[BEGIN]` messages and agent texts is absolute (`{work_dir}/iteration_NN/...`), exactly as `{compound_path}/analysis/...` is today.
- **`--ranking latest` in the frontier flow** (section Pitfalls 1).
- **Citing requirement IDs in skill text.** The lint pattern `\b(?!DEPT-)[A-Z]{2,5}-\d{2}\b` fails on `REC-25`; also no `D-NN`, no dates, no model IDs, no compound or dataset names, no capital-letter emphasis words, no "orchestrator" or "team lead" (`tests/test_skill_frontier.py:130-165`).
- **A new `.md` token that the dead-reference test does not know.** File names in skill prose must be packaged files or `CASE-PROGRESS.md`, `final_results.md`, `DIAGNOSTIC-REPORT.md` (`RUN_ARTEFACTS`, `tests/test_skill_frontier.py:35`).

## Common Pitfalls

### Pitfall 1: `--ranking latest` picks the cross-check
**What goes wrong:** the analyst's second call (`ailsa lsd rank <solutions.smi> --shifts ...`) records a nearest-line ranking as the newest; `finalize --ranking latest` declares against it, or refuses it, instead of the decisive atom-by-atom one.
**Why:** `resolve_ranking` takes the last `ranking.computed` (`finalize.py:73-78`); the analyst's workflow runs the assigned ranking first and the cross-check second (`ailsa-solution-analyst.md:78-101, 340`).
**How to avoid:** `[RANKING-COMPLETE]` names `Ranking id: rkNN` from the `ranking_id` field of the assigned call; the coordinator uses `--ranking rkNN`. Alternative: run the cross-check first. A reopen by the coverage gate or a new iteration after the ranking makes the ranking stale (`finalize` refuses): re-rank, then finalize.
**Warning signs:** `finalize` says the ranking was not written by the tool or is stale; the declared candidate has no atom map.

### Pitfall 2: teammates do not see the active run
**What goes wrong:** tools called by a teammate print "not recorded: no active run" and the iteration is missing from the record.
**Why:** resolution uses `AILSA_RUN_DIR`, the session pointer (session id), or the cwd marker. Ordinary subagents share the session id; real teammates are separate Claude Code instances and may carry a different session id or, in split panes, a different environment.
**How to avoid:** launcher start (sets `AILSA_RUN_DIR` and `AILSA_REQUIRE_RUN=1` in the lead's environment); in-process display only; agents' first action is a tool call whose stderr they must report if it contains "not recorded"; spawn prompts carry `{work_dir}` so the cwd marker (`<run>/.ailsa-run` above `agent/`) also works when a teammate runs `cd {work_dir}/...`. The proof run checks `tool.invoked` events with `agent_id` for every specialist.
**Warning signs:** `ailsa run status` shows zero iterations after a solver run; `tool.shell` events exist (hooks) while `tool.invoked` does not.

### Pitfall 3: writes into the dataset by accident
**What goes wrong:** a relative redirect or `mkdir analysis` from an agent whose cwd is the dataset folder lands in the dataset; REC-05 is violated and a later blind run sees "earlier results readable".
**Why:** the session's initial folder is the dataset in a slash start; subagent Bash calls start there.
**How to avoid:** absolute `<work_dir>` paths everywhere; the old `mkdir -p <compound_path>/analysis` and the manifest write are deleted; the acceptance check recomputes the dataset fingerprint after the run (as in 106.1-20).
**Warning signs:** `finalize` warns about files outside `agent/`; fingerprint changed.

### Pitfall 4: the runner loops forever
**What goes wrong:** with the old stop condition, `blind_case_run.sh` waits for `analysis/final_results.md`, which no longer appears, and burns eight resume attempts.
**How to avoid:** change the runner in the same phase (section 4); test it with a fake `claude` shim as `tests/record/test_launcher.py` does.

### Pitfall 5: compaction loses RUN and WORK
**What goes wrong:** after an automatic compaction the coordinator no longer knows `WORK` and writes elsewhere.
**How to avoid:** `case.md` says: after any compaction run `ailsa run init <dataset>` again (idempotent) to read `RUN:` and `WORK:`; the spawn prompts of the specialists carry `{work_dir}` so they are unaffected; hooks record `context.compacted`.

### Pitfall 6: smoke test and failure paths leave a running record
**What goes wrong:** a record that is never closed shows "run in progress" forever.
**How to avoid:** every exit path ends with `finalize` or `close` (table in Pattern 2); the launcher closes anyway; for slash starts the heartbeat marks "no heartbeat" after silence.

### Pitfall 7: notes over the cap or with Markdown breakage
Notes are capped at 4 000 characters and escaped by the renderer; long setup tables stay in the agents' messages and `WORK` files; the note holds a summary and the fields loop detection reads.

### Pitfall 8: the hook-less slash start
A slash-started session without installed hooks gets tool events but no agent attribution, no transcript copy and "not recorded by this harness". `ailsa run hooks install` (reversible) on the machine that runs interactive CASE sessions, or use the launcher. The skill's first step may print a one-line hint when `ailsa run status` reports `hooks_recorded: false` after the first agent turn; do not make it a gate.
