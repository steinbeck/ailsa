## Critical Issues

### CR-01: Watchdog abort sends SIGTERM to unrelated launcher runs of the same user on the shared host

**File:** `scripts/uat_watchdog.py:422-426` (also `:432-433`)
**Issue:** The new stop step is `pkill -TERM -f '[a]ilsa run start .*--skill ailsa'`. The regular
expression is unanchored, so it also matches `--skill ailsa-lite` (prefix match) and any
interactive frontier launch (`ailsa run start DATASET --skill ailsa --interactive …`). Checked:
`re.search` with the abort's pattern is True for
`ailsa run start /data/X --skill ailsa-lite --harness opencode …` and for
`ailsa run start /data/X --skill ailsa --interactive …`. `pkill` cannot signal other users without
root, but it terminates every matching process of `chris`. `abort_chunk()` runs automatically when
the seven-day quota passes the ceiling (`uat_watchdog.py:723-737`), which is the moment the owner is
most likely to be working interactively on the same host. The launcher treats SIGTERM as "kill the
harness tree and close the run as terminated", so an unrelated multi-hour interactive team run, or a
lean-skill experiment, is ended and its record closed without a result. The pre-existing KILL
pattern `--resum[e] .* --dangerously-skip-permissions` (line 433) has the same problem with SIGKILL:
it matches any resumed Claude Code session of the user started with that flag.
`tests/test_benchmark_scripts.py` checks only `claude -p hi`, `claude --resume …` and bare `claude`
as innocent command lines, none of which exercises the over-match.
**Fix:** Match only what the runner starts, or better, signal recorded PIDs:
```bash
# runner: record the launcher pid next to the results
"$AILSA_BIN" run start ... & LPID=$!; echo "$LPID" > "$RESULTS_DIR/launcher.pid"; wait "$LPID"
# abort: TERM exactly those pids
for f in "$CASE_RESULTS_ROOT"/CASE*/launcher.pid; do kill -TERM "$(cat "$f")" 2>/dev/null; done
```
If patterns stay, anchor them to the runner's exact argument order and the launcher's own nudge:
```bash
pkill -TERM -f '[a]ilsa run start [^ ]+ --skill ailsa --headless --blind '
pkill -KILL -f -- '--resum[e] [0-9a-f-]{36} -p Continue the CASE workflow where it stopped'
```
Add `--skill ailsa-lite …` and `--skill ailsa --interactive …` to the innocent list in the test.

## Warnings

### WR-01: Launcher crashes after an agent-side close when the transcript copy fails

**File:** `src/ailsa/record/launcher.py:682-694`
**Issue:** Plan 03 swallowed `RecordWriteRefused` for `run.attempt.ended` after the agent ran
`ailsa run close`, but the same refusal is still unguarded a few lines later. If
`_copy_transcripts` raises any exception other than a refusal (an `OSError` reading the transcript,
a permission error), the handler appends `warning.raised` to a finished run, which raises
`RecordWriteRefused`. It propagates through the `finally` (which still closes and renders) and out of
`launch()`. Reproduced in an isolated workspace with a fake `claude` that runs `ailsa run close` and a
`_copy_transcripts` that raises `OSError`: `launch()` raises
`RecordWriteRefused: run finished: post-run material goes to the verification store`. The CLI then
prints a traceback and no JSON, so the runner records `"status":"error"` (empty `run_id`) and skips the
compat copy even when the run declared a result before closing.
**Fix:**
```python
except Exception as exc:  # noqa: BLE001
    try:
        append_event(run_dir, "warning.raised", {...}, actor=_ACTOR)
    except RecordWriteRefused:
        sys.stderr.write(f"ailsa: transcript copy failed after close: {exc}\n")
```
Add a launcher test with `close_first` plus a failing transcript copy.

### WR-02: Runner copies and grades `inconclusive` declarations as if a candidate was proposed

**File:** `tests/case-benchmark/blind_case_run.sh:118-129`
**Issue:** The compat copy runs for every `RUN_STATE = result_declared`, and that state covers all six
declared outcomes. For `inconclusive --ranking rkNN` (the analyst trusts no candidate), the
rendering has no "Chosen candidate" block but still has the top-10 table. `grade_blind.extract_top_smiles`
puts the `| 1 |` row first (`grade_blind.py:61-62`), so the benchmark grades the rank-1 structure of
a run that explicitly declined to propose one, and can count it as solved at rank 1.
`handed_to_human`, `no_structure_fits` and `insufficient_data` also get `final_results: true` in
meta.json, so the watchdog treats them like answers. meta.json does not record the outcome, so the
grader cannot tell them apart afterwards.
**Fix:** Write the declared outcome into meta.json (`ailsa run status --run "$RUN_DIR" --format json`
gives `final.outcome`). Either copy only for `proposal` and `proposal_under_determined`, or keep the
copy and make the grader return `NO_RESULT` (or a separate `DECLINED` class) for the other outcomes.

### WR-03: meta.json drops the launcher's stop reason, so watchdog-aborted cases are retired as "exhausted"

**File:** `tests/case-benchmark/blind_case_run.sh:131-137`; `scripts/uat_watchdog.py:518-525`
**Issue:** On a quota abort the watchdog kills `blind_case_batch.py`, but not the bash runner. The
launcher gets SIGTERM, closes the run and emits `reason: "terminated"`, `signal: 15`, and exits
143. The runner treats only exit 2 as an error and writes meta.json without `reason`/`signal`.
`_PENDING_PROBE` then counts any meta.json with `runtime_s >= 600` as finished. A case the watchdog
itself aborted after ten minutes is never run again, and the batch skips it too because meta.json
exists. Re-running it by deleting meta.json now also fails: the per-case workspace
`$RESULTS_DIR/ailsa-runs` still holds the aborted run, so `--blind` refuses with exit 2. Neither the
README nor the runner says that `ailsa-runs/` has to go as well.
**Fix:** Copy `reason`, `signal` and `exit_code` from launch.json into meta.json. Have
`_PENDING_PROBE` keep a case pending when `signal` is set (or `reason` starts with
`terminated`/`interrupted`). Document that a re-run needs a fresh results folder, or move the aborted
record aside.

### WR-04: The runner's fence contradicts the skill's exit paths and forbids reading the run's own record

**File:** `tests/case-benchmark/blind_case_run.sh:81-83`
**Issue:** The fence says "do not stop until the run has declared its result with
`ailsa run finalize`". The skill ends the smoke test and every failure after `start_record` with
`ailsa run close` (`case.md:459-460`, `run-record.md:181-182`), and the launcher's own nudge allows
`close`. Under the fence a headless coordinator whose prerequisites fail, or which runs in smoke
mode, is pushed towards an unjustified declaration such as `insufficient_data`. That run would be
`result_declared`, get a compat copy and `final_results: true`, and the watchdog would retire a
broken-environment case as done. The fence also forbids reading "any … benchmark-results location",
while the run record the skill must read (`renderings/CASE-PROGRESS.md`, `{work_dir}/../rankings/`)
now lives under `$RESULTS_DIR/ailsa-runs/`. The instruction pair is self-contradictory, and the
combination was never run (see Summary).
**Fix:** Change the fence's last clause to "…until the run is settled: `ailsa run finalize` with a
justified outcome, or `ailsa run close --reason …` when no result can be declared". Exempt the run
folder explicitly: "your own run folder (the parent of your working folder) is not a results
location; other folders under the results root are".

### WR-05: Default results folder puts the blind agent's working folder inside the repository

**File:** `tests/case-benchmark/blind_case_run.sh:94`; `tests/case-benchmark/README.md:21-22`
**Issue:** The old runner started Claude Code in a `mktemp` scratch folder precisely so that no project
memory applies. The launcher's harness now starts in `$RESULTS_DIR/ailsa-runs/<run>/agent`, and the
batch's default results root is `tests/case-benchmark/results` inside the checkout
(`blind_case_batch.py:37`). Claude Code reads `CLAUDE.md` from the working folder and every parent
folder, so a blind run started the way the README's "Typical run" shows loads the repository's
developer `CLAUDE.md`. That file names the private local file that maps the example datasets to
their identities (`.planning/CASE-DATASET-IDENTITIES.md`, untracked but present in local
checkouts). The README still promises "a neutral scratch cwd (no project memory)". The watchdog
passes an external results folder, so Sheldon series are not affected; manual or local batches are.
**Fix:** Refuse a results root inside a git work tree in the runner, for example
`git -C "$RESULTS_DIR" rev-parse --is-inside-work-tree 2>/dev/null && { echo "results inside a repo" >&2; exit 2; }`,
and move the default results root out of the repository (for example `${XDG_STATE_HOME:-$HOME/.local/state}/ailsa-bench`).
Correct the README sentence.

### WR-06: Runner silently runs whichever `claude` comes first on PATH; meta.json still names the pinned binary

**File:** `tests/case-benchmark/blind_case_run.sh:57-58, 78-79`; `src/ailsa/record/launcher.py:153-154`
**Issue:** The launcher always runs the harness by the name `claude`. The runner tries to pin
`$CLAUDE_BIN` by prepending its folder to PATH, which works only if the binary's basename is
literally `claude`. A bare name (`CLAUDE_BIN=claude-2.1.332`) or a differently named file does
nothing, and the comment at `uat_watchdog.py:430-431` says the pinned binary "need not end in
'claude'". `child_environment` then puts the venv's `bin/` before the pinned folder, so a `claude`
there wins. In each of these cases meta.json records `claude_bin`/`claude_version` from
`$CLAUDE_BIN --version` while a different CLI ran, which defeats the stated reason for pinning
(comparability within a series).
**Fix:** In the runner, refuse when `basename "$CLAUDE_BIN"` is not `claude` or when
`PATH=… command -v claude` does not resolve to `$CLAUDE_BIN`. Better: give the launcher a
`--harness-bin PATH` option that `build_argv`/`build_resume_argv` use as `argv[0]`, and record the
resolved binary and its `--version` in `run.attempt.started`.

### WR-07: Rendered result can show the identity of rank 1 next to a chosen candidate of another rank

**File:** `src/ailsa/skills/ailsa/agents/ailsa-solution-analyst.md:218, 264, 327`; `src/ailsa/record/render.py:230-239`
**Issue:** This phase made the declared candidate explicitly "not always 1" (analyst's declaration

### WR-08: After a coverage reopen, the identity gate and the declaration draft use the stale ranking message

### WR-09: Slash-started runs stay open and session-bound after `finalize`; a second `/ailsa:case` reuses the old run

**File:** `src/ailsa/skills/ailsa/commands/case.md:136-138, 445-465`; `src/ailsa/skills/ailsa/references/run-record.md:167-182`
**Issue:** `case.md` states that every exit ends with `finalize` or `close` "so no record is left
open". `finalize_run` never appends `run.finished`, and the terminate step never closes a declared
run, so in a slash start (no launcher to close it) the record stays open and the session pointer
stays bound. If the user starts `/ailsa:case` again in the same session on the same dataset,
`init_run` step 3 returns the old run (`runinit.py:368-377`, `created: False`). The second attempt's
events, notes and solver rounds land in the first run's record. Its agents work in the same
`{work_dir}`, where the engineer's "read the previous LSD file" rule picks up the first attempt's
`iteration_NN/compound.lsd`. Its declaration supersedes the first one. Any tool step a specialist
runs after the declaration (still possible during shutdown in a team) marks the declaration stale.
**Fix:** In terminate_team, after `finalize` and `render`, close the record with
`ailsa run close --reason "declared"` (the state stays `result_declared`, because the fold derives it
from the declaration first; under the launcher the launcher's own close is then refused and handled
quietly). Alternatively, make `run init` refuse to reuse a session run that already holds a valid
declaration. Correct the "no record is left open" sentence either way.

### WR-10: Recorded frontier skill version comes from the packaged copy, not the installed one

**File:** `src/ailsa/record/runinit.py:150-165`; `src/ailsa/record/env.py:192-229`
**Issue:** For the command skill, `_skill_location` returns the *packaged* folder as `skill_dir`, so
`skill_info` reads `name`/`version` from the packaged `INDEX.md`, and only `files` is replaced by the
installed hashes. After a copy install of an older version (`ailsa skill install ailsa --target claude`
without `--link`), `env.captured` reports `skill.version: 0.2.0` and location
`global-claude-commands` while 0.1.0 actually ran. Only `skill_matches_packaged: false` hints at the
mismatch. The record's per-run skill version, which identifies the skill behind a run, is then
wrong. Both `command_skill_files` and the launcher's install check also hard-code `~/.claude` and
ignore `CLAUDE_CONFIG_DIR`, which Claude Code honours.
**Fix:** When `installed is not None`, read name and version from `~/.claude/ailsa/INDEX.md` (the
installed file) and add `packaged_version` separately. Resolve the Claude folder once
(`Path(os.environ.get("CLAUDE_CONFIG_DIR", Path.home() / ".claude"))`) and use it in `env.py`,
`runinit.py` and `launcher.py:209`.
