# Phase 106.1: Run record core - Context

**Gathered:** 2026-11-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Every new run writes a structured run record in its own folder in a workspace outside the
dataset: a manifest, an append-only event log with a hash chain, typed results written by tools,
and an explicitly declared result. `ailsa run render` turns the record into Markdown. The record
lives in the `ailsa` package (commands + Claude Code hooks), not in a skill.

**This phase is the package half plus the lean skill** (decision D-01/D-02 below):
- the recording commands, the launcher, the hooks, remote solves, spectra view products and the
  renderer, all in `src/ailsa/`;
- the lean skill `ailsa-lite` (`src/ailsa/skills/ailsa-lite/`) wired to them;
- done when a lean run writes a valid record (plus the automated tests listed under D-15).

**Not in this phase:** wiring the frontier skill (`.claude/commands/lucy-ng/`, `.claude/agents/lucy-*.md`)
and proving team and headless runs. That moves to a new small follow-up phase after Phase 106
(skill rename), see Deferred. The frontier skill and the old web view stay untouched here.

Requirements: release R0a of the web-interface spec (draft 2.3, §4): REC-01 to REC-07, REC-09 to
REC-20, REC-22 to REC-25, REC-27 to REC-29, REC-31, REC-33. Where a requirement names both skills
(REC-03) or a team (REC-25 per agent), this phase delivers the package side and the lean skill;
the frontier side follows in the follow-up phase.

</domain>

<decisions>
## Implementation Decisions

Owner decisions already taken in the spec (SPEC §13, "Owner answers", 2026-11-24) are not
repeated here; they are binding: SPEC D1 (structured record, strict for the final result,
warnings elsewhere), SPEC D4 (one folder per run in a workspace outside the data), SPEC D5
(read-only interface; a run is "assisted" if a human message carried chemical content), SPEC D15
(tool steps and the final declaration first; full decision recording only after measuring its
effect), SPEC D16 (raw transcripts leave the machine only on explicit request).

### Sequencing
- **D-01:** Build the package part now (recording commands, launcher, hooks, remote solve,
  renderer, spectra export) and wire the lean skill now. The frontier skill is wired only after
  the Phase 106 rename, so its ~900-line coordinator file is touched once, in its renamed and
  split form. Do **not** edit `.claude/commands/lucy-ng/` or `.claude/agents/lucy-*.md` in this
  phase (they are also under a SHA-256 byte guard).
- **D-02:** Split the phase. 106.1 closes when a lean run writes a valid record. A new follow-up
  phase after Phase 106 wires the frontier skill and proves the team run and the headless run
  (roadmap success criterion 1 for those two run types moves there). The roadmap entry of 106.1
  must be adjusted and the follow-up phase inserted (see Deferred).

### Workspace and run folders
- **D-03:** Workspace default `~/ailsa-runs` on every host; overridable by an environment variable
  or an entry in an `ailsa` configuration file (no config mechanism exists yet; design one). On
  Sheldon the workspace will be `/mnt/raid_drive/chris/ailsa-runs` (home disk 77 % full). Works
  without any setup step.
- **D-04:** Blind protection: `ailsa run init`/`start` recognises "the same dataset" by a content
  fingerprint of the raw data (survives folder renames). In blind mode it refuses to start if the
  workspace holds an earlier run on the same dataset, with a clear message. An explicit option
  (spec name `--allow-prior-runs`) starts anyway and marks the run permanently "not blind: earlier
  results were readable". No additional Claude Code read-deny rules (rejected: harness-specific
  and bypassable).
- **D-05:** Two ways to create the record, same result:
  - a launcher `ailsa run start <dataset>` creates the run folder, captures the environment
    (REC-24/25), and starts Claude Code or OpenCode inside it with the skill; meant for headless and
    benchmark runs;
  - for a run started by a slash command inside an open session, creating the record is the
    skill's first step.
- **D-06:** Run folder name = UTC start time + dataset folder name + short random part, e.g.
  `2026-11-24T1417Z_terpineol_k3f9`. In blind mode only the dataset folder name the agents see
  anyway (e.g. `CASE175`). The dataset label is still stored as a separate manifest field (REC-07).

### Strictness on gaps
- **D-07:** An `ailsa` tool called during a run that cannot find its run works normally and
  prints a clear warning "not recorded: no active run" in its output (text and JSON), so the agent
  can react. A run never aborts over bookkeeping. Outside any run (manual use) tools behave as
  today. The Claude Code hooks independently log every shell command, so such calls stay visible.
- **D-08:** Each run folder has an agent working subfolder. Anything agents write goes there and
  is shown as "unverified". A file an agent places elsewhere in the run folder is reported as a
  warning by `ailsa run finalize` and shown as unverified; nothing is blocked; no Claude Code
  write lock.
- **D-09:** A broken hash chain: readers (`ailsa run render`, later the viewer) show everything,
  mark "record changed or incomplete from here" from the break onward, and the run never counts as
  clean in any evaluation. (A truncated last line after a crash is the expected common case; it
  must still render.)
- Already fixed by spec/roadmap, restated for the planner: a run without a valid declaration, or
  whose ranking was hand-formatted, ends "stopped before a result (inferred)"; `finalize` refuses a
  missing, invalid or stale ranking (LSD input hash mismatch) but accepts outcomes without a chosen
  candidate (inconclusive, no structure fits, handed to a human, …); harnesses without hooks show
  hook items as "not recorded by this harness".

### Transition of old files
- **D-10:** Prose progress notes go through a note command (working name `ailsa run note "…"`):
  sender and UTC time are added automatically, the note becomes an event in the log. The progress
  log (`CASE-PROGRESS.md` or its successor) is rendered from tool events plus notes and is never
  edited by hand. Agents can still read the rendered log (loop detection). For the lean skill this
  phase; for the frontier skill in the follow-up phase.
- **D-11:** The old web view (`ailsa webview`, `src/ailsa/webview/`, auto-launched by the frontier
  skill) is removed in the follow-up phase together with the frontier wiring. In this phase it
  stays untouched; the current frontier skill keeps running unchanged.
- `final_results.md` becomes a rendering of the `finalize` declaration plus the tool-written
  ranking (REC-22); narrative assessment goes into the declaration's confidence / caveats / open
  questions / next steps fields (REC-16).

### Acceptance (what proves this phase)
- **D-12:** Real agent run: one lean run on α-terpineol (public BMRB bmse000667; processed data at
  `~/Dropbox/develop/data/nmrdata/ailsa-example-terpineol/run-data-v3`, a copy is on Sheldon) on
  Sheldon, with a small Claude model in Claude Code; it must leave a valid record including the
  hook items. Expected under an hour. No Opus run, no OpenCode/Qwen run.
- **D-13:** Automated tests in any case:
  - a hand-formatted ranking ends "stopped before a result (inferred)";
  - a simulated harness without hooks shows hook items as "not recorded by this harness";
  - hash-chain break handling (D-09), blind refusal (D-04), the warning path (D-07);
  - `ailsa run render` output from a fixture record.
- **D-14:** Remote solve: a solve started on vitus with `ailsa lsd run --host sheldon` is recorded
  locally with host, LSD version and binary hash, timing, outcome class (REC-31).
- **D-15:** The α-terpineol raw data stay out of the repository (BMRB asks only for
  acknowledgement, names no licence): a download script plus the processing script
  (`.planning/research/webview-redesign/example-terpineol/process_fid.py`, to be moved into the
  repo proper) and the BMRB credit come instead. Tests that need the data skip when it is absent.

### Claude's Discretion
- Record file layout, schema format and versioning; event type names; how a tool finds the
  active run (environment variable, pointer file, explicit flag — must work for subagents and in
  OpenCode); lock mechanism for the append-only log.
- Whether the lean skill's existing first command (`ailsa case setup`) doubles as record creation
  or the skill gets an explicit `ailsa run init` step. Fewer steps are better for small models.
- How hooks are installed (plugin hooks, or per-run `.claude/settings.json` written by the
  launcher) as long as they are no-ops outside a run and work for both D-05 start paths.
- How the lean skill's state (`analysis/problem.json`, today inside the dataset) moves into the run
  folder; NUS reconstructions must stop writing into experiment folders (REC-05).
- Exact name of the workspace environment variable and config file location.
- Which small Claude model runs the D-12 acceptance run.

- `src/ailsa/case/` (lean-skill engine, ~2.9k lines): `model.py` keeps run state in

  first writers of typed results; currently write into `<dataset>/analysis/` (must move, REC-05).

  `--analysis` override for the state folder.
- `src/ailsa/cli/lsd.py` — `lsd run` (local only, no `--host`), `lsd rank`, `lsd analyze`,
  `lsd validate-inventory`. REC-14/15/20/31 attach here.

  path that REC-29 view products must share (same referencing as the pickers).

- Every subcommand supports `--format json` (except setup commands and `visualize`).

- The frontier skill today writes `analysis/.run_manifest.json` (two fields), `timing.jsonl`
