## Summary

The record can be built entirely on the standard library plus the dependencies `ailsa` already has (click, pydantic
v2, numpy, nmrglue, jsonschema). No new package is needed. The hard parts are not the log format but four
integration facts found in this research. First, `ailsa` is slow to start (1.9 s CPU for `ailsa --version`, measured
on the dev host) because `ailsa/__init__.py` eagerly imports rdkit, scipy and nmrglue and `cli/main.py` imports every
command module; REC-04 ("well under a second") and every hook invocation are impossible until startup is made lazy.
Second, the lean skill the CONTEXT describes (`ailsa case` state in `analysis/problem.json`) was withdrawn in lean
skill 0.2.0: the current skill has the agent write `setup.md`, `iteration_NN/compound.lsd` and `final_results.md`
itself and calls `pick`, `lsd run`, `lsd rank --assigned`, `lsd analyze`, `identify`. The `ailsa case` engine is
therefore not the place to attach record writers; the writers attach to those tools. Third, Claude Code exposes the
session id to Bash subprocesses and hooks (`CLAUDE_CODE_SESSION_ID`, same value as the hook JSON `session_id`), which
makes a reliable "which run is this session" lookup possible for the slash-command start path without any agent
cooperation. Fourth, non-interactive `ssh host cmd` on Sheldon has no `~/.local/bin` in `PATH` (LSD, claude not found)
and Sheldon's binary is lowercase `lsd`; remote solves must run under `bash -lc` or a configured absolute path.

**Primary recommendation:** Build a stdlib-only `ailsa.record` core (workspace/config, flock+O_APPEND hash-chained
`events.jsonl`, pure reducer to `manifest.json`), make `ailsa` start lazily, add one generic wrapper on the click group
so every tool call records itself in a run context, resolve the active run by `--run` > `AILSA_RUN_DIR` >
session pointer file keyed by `CLAUDE_CODE_SESSION_ID` > cwd marker, install hooks per run via `claude --settings`
(launcher) and via a one-time `ailsa run hooks install` (open session), and make `finalize` accept only a ranking
whose file hash equals the `ranking.computed` event hash.

### Pattern 2: Event envelope, chain and writer

**What:** One JSON object per line. `prev` = SHA-256 (hex) of the **raw bytes of the previous line without the
trailing newline**, so verification never depends on JSON canonicalisation. Genesis `prev` = `sha256(run_id)`.
Fields follow [02 §4.6] with `refs`/`payload`, plus the TL-13..15 needs (sender, receiver, kind, time, one line):
agent messages are typed events with `payload.from`, `payload.to`, `payload.kind`, `payload.text` (and an optional
`payload.line` slot that REC-34 will fill later without migration).

```jsonc
{"v":1,"seq":171,"utc":"2026-11-24T14:22:57.412Z","host":"sheldon","type":"solver.finished",
 "actor":{"kind":"tool","name":"ailsa lsd run"},"span":{"id":"sp:it05","parent":"sp:run"},
 "refs":["it05"],"payload":{"outcome":"limit_reached","count":20000},"prev":"<64 hex>"}
```

**Writer (stdlib, ~40 lines; the shape to implement):**

```python
# Source: man flock(2) / Python docs (fcntl, os); design is this research's recommendation
import fcntl, hashlib, json, os, time

def append_event(run_dir, make_event, *, lock_timeout=10.0):
    lock_fd = os.open(os.path.join(run_dir, "events.lock"), os.O_CREAT | os.O_RDWR, 0o644)
    deadline = time.monotonic() + lock_timeout
    while True:
        try:
            fcntl.flock(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB); break
        except BlockingIOError:
            if time.monotonic() > deadline: raise TimeoutError("events.lock busy")
            time.sleep(0.02)
    try:
        path = os.path.join(run_dir, "events.jsonl")
        fd = os.open(path, os.O_CREAT | os.O_RDWR | os.O_APPEND, 0o644)
        try:
            seq, prev, partial = tail_state(fd)            # reads last <=64 KiB; see below
            if partial:                                    # last line has no "\n": crash residue
                os.write(fd, b"\n")                        # keep the bytes as evidence, never truncate
            ev = make_event(seq=seq + 1, prev=prev)        # prev = sha256(raw last line bytes)
            line = json.dumps(ev, separators=(",", ":"), ensure_ascii=False).encode()
            os.write(fd, line + b"\n")                     # one write under the lock
        finally:
            os.close(fd)
    finally:
        fcntl.flock(lock_fd, fcntl.LOCK_UN); os.close(lock_fd)
```

`tail_state` rules (D-09): if the file ends with `\n` take the last line; if it does not, the tail is a partial line:
the writer appends `\n`, then emits a `log.recovered` event whose `prev` is the hash of the partial bytes and
whose payload records `discarded_bytes`. Readers parse line by line; a line that is not valid JSON, has a wrong
`seq`, or a `prev` mismatch starts the "record changed or incomplete from here" zone: everything after is still
rendered but flagged, and `manifest.integrity = {"clean": false, "first_bad_seq": n}`. A truncated final line is
reported as `incomplete` (crash), not `tampered`. `os.fsync` only for lifecycle/finalize events (process crash
needs no fsync; power loss does).

**Honest scope of the chain:** it makes accidental edits, truncation and out-of-band writes visible. It is not
protection against a writer who recomputes every hash (no secret key). Store `chain_head` in the manifest and in the
workspace index at `run.finished` so a later change of the log is visible against two places. Do not oversell it in
docs.

### Pattern 3: Finding the active run (answer to research question 2)

Resolution order, first hit wins; every candidate is checked (directory exists, marker valid, not finished):

| # | Source | Works for | Failure mode |
|---|--------|-----------|--------------|
| 1 | `--run PATH\|ID` on `ailsa run …` commands | explicit use, tests, scripts | none |

`AILSA_REQUIRE_RUN=1`. A lean session whose agent skipped `run init` then prints nothing, so the lean skill must make

### Pattern 4: Tools record themselves (REC-04)

A custom `click.Group` subclass on the root `cli` overrides `invoke(ctx)`: resolve run (cheap), run the command,
then append one `tool.invoked` event: argv (long values truncated), exit code, duration, size and sha256 of stdout.
`ailsa run *`, `--help`, `skill`, `database` are excluded (no recursion, no noise). Typed commands (`pick`,
`lsd run/rank/analyze/validate-inventory/import`, `identify`, `spectra export`, `nus …`) additionally write their
typed artefact and event through `ailsa.record.artefacts.register(...)`. The wrapper must never raise: any record
failure becomes one stderr line "record write failed: …" (D-07 spirit: a run never aborts over bookkeeping).

### Pattern 5: `lsd run` keeps the agent's workflow, registers by hash

The lean skill runs `cd iteration_NN && ailsa lsd run compound.lsd`, then `ailsa lsd rank --assigned
iteration_NN/compound.lsd` which reads `compound.sol` next to the input (`rank_assigned` uses
`lsd_file.with_suffix(".sol")`). Keep those command lines unchanged:

1. `lsd run` executes as today in the agent's iteration dir (or remotely, then fetches back into it).
2. In a run context it then registers: copies input, filter files, `.sol`, `solutions.smi`, `solncounter` into
   `<run>/iterations/itNN/` (authoritative copy), writes `solver.json` (outcome enum, count, limit, elapsed, exit
   code, LSD version/hash, host, absence reason) and emits `lsd.input.registered` (iteration, parent, purpose, hash,
   unified diff against the parent input, LSD index map parsed from `MULT` lines) and `solver.finished`.
3. `lsd rank --assigned` and `lsd analyze` in a run context locate the iteration by the **sha256 of the given input
   file**, read the authoritative `.sol`, and warn if the agent-dir copy differs. The resulting `ranking.json`
   contains `inputs: [{iteration, lsd_sha256, sol_sha256}]`. `finalize` compares them with the latest registered
   inputs: mismatch = stale = refuse.

Iteration ids `it01, it02, …`; `--purpose main|family|diagnostic|control` (default main) and `--parent itNN`
(default: the latest main iteration). The id mapping is printed in the command output so the agent can reuse it.

### Pattern 7: Remote solve (REC-31, answer to question 5)

1. Validate alias: `^[A-Za-z0-9][A-Za-z0-9._-]*$` (must not start with `-`, ssh option injection) and always pass
   `--` before the host.
2. Stage locally in a temp dir: input file, the bundled `ring3`/`ring4` (`LSDInputGenerator._write_filter_files`) and any
   file named in `DEFF`/`FEXP` lines of the input (parsed, basename only, no path separators).
3. One probe round trip: `ssh -o BatchMode=yes -o ConnectTimeout=15 -- ALIAS 'bash -lc "…"'` that creates a scratch dir
   (`mktemp -d`), resolves the LSD binary (**case: macOS `LSD`, Sheldon `lsd`; try both**), runs it with `</dev/null`
   in an empty dir for the banner (`LSD-3.4.9` is the first line; `--version` prints the same banner and an error),
   and `sha256sum` (Linux) / `shasum -a 256` (macOS) of LSD and outlsd. `outlsd` has **no version banner** (it prints
   usage), so record `version: null` plus the hash.
4. Upload with `tar cf - . | ssh … 'cd scratch && tar xf -'` (single connection), then start LSD **detached**
   (`setsid nohup bash -lc 'cd SCRATCH && timeout T lsd compound.lsd >lsd.out 2>lsd.err; echo $? >rc'`) and poll with
   short ssh calls every ~10 s (reading `rc` and `solncounter`). A dropped connection (laptop sleep, network change)
   then does not kill the solve; polling resumes. `timeout` exists on Sheldon (`/usr/bin/timeout`); on a macOS compute
   host use `gtimeout` or poll-side kill.
5. Fetch `*.sol`, `solncounter`, `lsd.out/err`, run `outlsd 5 < compound.sol > solutions.smi` remotely (the `.sol`
   can be large: 18 MB seen in 02), fetch into the agent iteration dir, then register locally exactly like a local
   run (host alias, banner, binary hashes, `elapsed_s`, `timeout_s`). Remove the scratch dir last; leave it in place
   and record its path if fetching failed.
6. Nothing is ever written into the run folder by the remote side. Output brought in any other way:
   `ailsa lsd import ITERATION_DIR` registers it with `provenance: "imported, not run by the tool"`.

PATH pitfall (verified): on Sheldon a non-interactive `ssh sheldon command -v lsd` finds nothing; under `bash -lc`
it finds `/home/chris/.local/bin/lsd`, `outlsd` and `claude`. Allow an explicit per-host override in `config.json`
(`hosts.<alias>.lsd`, `.outlsd`). Do not put any IP, user or path of the compute host into tracked files; the alias
comes from the user's `~/.ssh/config`.

### Pattern 8: Dataset fingerprint (answer to question 8, measured)

`sha256` over the sorted list of `(path relative to the dataset root, size, sha256 of content)` for every file,
excluding `analysis/`, `.DS_Store`, and anything under a run folder. Relative paths make it survive renaming the
dataset folder (D-04); no mtimes (Dropbox and copies change them).

Measured on this laptop (warm cache), CASE6 (459 files, 243 MB, the largest dev dataset except one JCAMP): full
content hash 0.64 s; sampled hash (whole file ≤ 4 MiB, else first+last MiB) 0.34 s. Both are cheap, so use the **full
content hash** (matches [02 §4.3]); fall back to the sampled form only for files > 256 MiB and record
`fingerprint_mode` in the manifest. Never grep binary NMR data. The prior-run scan reads the first line of
`events.jsonl` (the `run.created` event carries the fingerprint) of each run folder in the workspace; O(#runs) opens;
`runs.json` is the rebuildable convenience index. Two simultaneous starts on one dataset race: do the check-and-create
under a workspace-level lock file (`<workspace>/.lock`).

Blind-mode caveats worth stating in `ailsa run start --help`: the workspace is readable by the agent (D-04 rejected
deny rules), so the refusal is protection against accident, not against an agent that explores `..`; the manifest
records `prior_runs_readable: true/false` for that reason. Per-run cwd also gives each run its own Claude Code
auto-memory folder (`~/.claude/projects/<encoded cwd>/memory`), which removes the old per-data-dir memory leak path;
the launcher should additionally pass `{"autoMemoryEnabled": false}` in its `--settings` [CITED:
code.claude.com/docs/en/settings-reference, key exists, scope "Any file"].

### Pattern 9: Spectra view products (answer to question 6)

No new dependency, no zarr. Per experiment and processing state, `spectra/<exp_id>/<view>/`:

- `view.json` (`schema: ailsa.spectrum-view`, `schema_version: "1.0"`): kind, nuclei, spectrometer frequency per
  axis, ppm start/end, points per axis, `noise_sigma` (reuse `_compute_2d_noise_sigma` MAD in
  `processing/peak_picker_2d.py` and the 1D MAD of the pickers), quantisation parameters, per-level shapes and
  files, sign meaning (edited HSQC/DEPT), processing state enum (`vendor`, `rawproc`, `nus-smile`, `nus-vendor`,
  `agent-script`), source file hashes, reader version, referencing applied, suggested contour levels (multiples of
  sigma).
- 1D: `data.f32` little-endian float32 at full resolution (≤ ~0.5 MB for 128 k points).
- 2D: `level0.i16 … levelN.i16` (full resolution, then ≤ 1024-cap, 512, 256), little-endian int16.
  Quantisation (noise-normalised, log): `z = data / sigma`; `q = round(sign(z) * 32767 * log1p(|z|) / log1p(zmax))`
  with `zmax = max|z|` stored in `view.json` so a viewer inverts with `expm1`. **Signed max-abs pooling** per block:
  reshape to `(H/f, f, W/f, f)`, take the element of largest `|value|` per block (`argmax` on `abs`, then
  `take_along_axis`) so small cross-peaks survive downsampling; pad to a multiple of `f` with zeros.
  Projections `proj_f1.f32`, `proj_f2.f32`: max-abs skyline in z-space.
- Raw-only experiments (7 of the 13 dev datasets' experiments) go through the same processing the pickers use
  (`case/rawproc.py`); state `rawproc`. Experiments the readers reject (`Spectrum2D.experiment_type` accepts only
  HSQC, HMBC, COSY, TOCSY, NOESY, ROESY) appear in the inventory with `view: null` and a reason.
- Size per run [ASSUMED from [02 §5.3], to be measured on the terpineol set and CASE6]: tens of MB for 7–12
  experiments (a 4096×2048 int16 level 0 is 16 MB; a 1024² level is 2 MB; first paint ≤ 3 MB).
- `run init` calls the export inline for processed experiments (REC-29: "generated at run start"). Measure on CASE6
  in Wave 0; if one export exceeds ~20 s on the dev host, switch to a single detached child process (never a
  multiprocessing pool: see the orphan-worker lesson) that emits `spectrum.processed` events as it goes, and make
  `finalize` wait for it or mark "views pending".

### Pattern 10: Inventory (REC-28)

Reuse `case/scan.py` (`scan_dataset`, `read_experiment`, `classify`): it reads only `acqus`/`acqu2s`, never the
title, aliases non-numeric folder names to `x1…` so a compound name in a folder name is never shown, and already
yields kind, pulse program, nuclei, scans, solvent, processed/raw, edited. Add to the parameter read: `SFO1` per
axis (spectrometer frequency), `TE` (temperature), NUS (`NusAMOUNT`, presence of `nuslist`; reuse
`nus/params.py` `NusAcquisitionParams`), spectral width. The `Experiment` dataclass is also used by the withdrawn
`ailsa case` code; adding fields is safe. JCAMP: record file list and `##` header fields only (never `TITLE`/`OWNER`);
views for JCAMP may be deferred (discretionary, acceptance data are Bruker).

### Anti-Patterns to Avoid
- **Importing pydantic, numpy or `ailsa` top-level in the hook or log writer.** `ailsa/__init__.py` imports rdkit, scipy, nmrglue: `python -m ailsa.record.hook` costs seconds unless `__init__` is lazy (Pitfall 1).
- **Shell-interpolating hook payload text** (prompts, commands) anywhere. Use exec-form hooks (`command` + `args`), `subprocess` with argv lists, `shlex.quote` for the remote script.
- **Truncating a damaged log tail.** Keep the evidence; append a recovery event.
- **Deriving the final status from the agent's files.** Status comes from `final.declared` events only; a hand-written `final_results.md` or ranking is "unverified".
- **Running `lsd rank` against a `.sol` that was edited.** Compare `sol_sha256`.
- **One global `--run` option on the root group.** It changes the signature of every command the contract test inspects; use env/pointer discovery plus `--run` only on `ailsa run …`.

### Where hooks come from, and the no-op rule

- Hook locations: `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed
  settings, plugin `hooks/hooks.json`, skill frontmatter, subagent frontmatter [CITED]. Entries **merge** across
  levels. `--settings <file-or-json>` is applied above user/project/local files and below managed settings; "most
  lists merge" with file-based values [CITED: settings doc, cli-reference]. Edits to settings files, including
  `hooks`, are picked up by a running session [CITED: settings doc, "When edits take effect"].
- **Interactive sessions hold back hooks from every settings file, including `~/.claude/settings.json`, until the
  folder's workspace trust dialog is accepted. `-p` sessions never show the dialog and treat the folder as trusted**
  [CITED: hooks doc, "Workspace trust"]. Consequence: headless/benchmark launcher runs are unaffected; an interactive
  launcher run in a brand-new run folder shows the trust dialog once per folder (or inherits trust from a trusted
  parent such as the workspace). Document it; D-12 uses `-p`.
- **Launcher path (certain):** write `<run>/hooks.json` and start `claude --settings <run>/hooks.json …`. The hooks
  exist only for that session, so they are no-ops elsewhere by construction.
- **Open-session path (slash command):** hooks must already exist. Default recommendation: a one-time
  `ailsa run hooks install` that merges the same hook set into `~/.claude/settings.json` (backup first, merge into
  existing arrays, tagged so `hooks uninstall` removes only ours; the owner's file already carries other hooks). Every
  hook invocation first resolves the run (Pattern 3) and exits immediately when there is none, so unrelated sessions
  and the unchanged frontier skill are unaffected apart from ~40–60 ms process start per event [VERIFIED:
  `python -c pass` = 0.04 s; with lazy imports expect the same order]. Use `async: true` for the frequent
  observational events (`PostToolUse`) and synchronous for the rare ones (`Stop`, `SessionEnd`, `PreCompact`, `Subagent*`).
- **Candidate that avoids touching user settings:** `hooks:` in the lean SKILL.md frontmatter ("registered when the
  skill is invoked, kept for the rest of the session", removed on `/clear`/`/resume`; no effect before invocation)
  [CITED: skills doc, hooks doc]. Unclear which events frontmatter accepts and whether `SessionEnd`/`Stop` work;
  `once` only applies there. Spike it in Wave 0 (Open Question 1). It would also be ignored by OpenCode, which is fine.
- Plugin-shipped hooks: possible but need plugin packaging and install (`--plugin-dir` per session); not worth it
  for this phase. A plugin hook's `timeout` also does not raise the SessionEnd budget.
- **Hook command form:** exec form `{"type":"command","command":"<abs python>","args":["-m","ailsa.record.hook"],"timeout":10}`;
  `<abs python>` = `sys.executable` of the environment that generated the file (re-run `hooks install` after moving a
  venv). The hook reads the event name from `hook_event_name` in the JSON.
- **The hook must never disturb the agent:** swallow every exception, always `exit 0`, print nothing to stdout
  (stdout is added to the context on `UserPromptSubmit`/`SessionStart`), log failures to `<run>/hook-errors.log`.
  Exit 1 would print a "hook error" notice into the transcript; exit 2 would block.
- `SessionEnd` has a default budget of 1.5 s (raised by per-hook `timeout` in settings files up to 60 s, or
  `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`; the launcher sets the env var to 15 000) [CITED: hooks doc].

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| File locking | lock files with PID polling | `fcntl.flock` on a dedicated `events.lock` | released automatically when the process dies |
| Atomic JSON writes | write-then-hope | `tempfile` in the same dir + `os.replace` (+ fsync for finalize) | crash safety, readers never see half files |
| Hashing the log | custom canonical JSON | sha256 over raw line bytes | no canonicalisation bugs |
| Experiment classification | new scanner | `ailsa/case/scan.py` | already never reads titles, aliases folder names |
| 2D noise estimate | new estimator | `_compute_2d_noise_sigma` in `processing/peak_picker_2d.py` | same sigma the pickers use (REC-29 consistency) |
| Atom map and per-atom stats | new ranking code | `ranking/assigned.py` (`_molecule`, `AtomError`, `PredictedShift`) | already computed, just discarded |
| LSD error line | regex again | `LSDRunner._lsd_error` | existing, tested |
| Partial solution count | parse `.sol` | `solncounter` as `case/solve.py` does | LSD writes it while running |
| JSON Schema | hand-written | `BaseModel.model_json_schema()` + drift-guard test | single source of truth |
| ULID/UUID | custom | `secrets`, `uuid.uuid4()` for the launcher's `--session-id` | stdlib |

**Key insight:** every difficult piece (atom map, per-atom predictions, noise sigma, scan, error line, partial count)
already exists in the code and is merely not persisted. The phase is mostly about persisting existing results in typed
form and wiring discovery, not about new algorithms.

## Common Pitfalls

### Pitfall 1: `ailsa` starts in ~2 seconds, hooks and recording commands cannot be fast
**What goes wrong:** `ailsa --version` = 1.87 s user, 3.3 s wall [VERIFIED: measured]; `import ailsa` alone is 1.7 s.
Import profile: `ailsa/__init__.py` pulls `database.importer` (rdkit), `detection`, `lsd.generator`, `analysis`,
nmrglue (1.24 s alone) and scipy.signal (1.16 s). `click`+`pydantic` cost 0.09 s; `rdkit.Chem` 0.13 s; numpy 0.10 s.
**Why:** eager imports in `ailsa/__init__.py` and in `cli/main.py` (every command group imported at top level);
`ailsa.lsd.__init__` does `from ailsa import BrukerReader, DEPTGuidedPicker`.
**How to avoid:** Wave 0 task: (1) make `ailsa/__init__.py` lazy with PEP 562 `__getattr__` (public names keep
working: `from ailsa import BrukerReader`, doctests, `ailsa.lsd.__init__`), (2) a lazy click group (`LazyGroup`) that
imports a command module only when invoked or when help needs it, (3) keep `ailsa.record` stdlib-only at import
time. Test: spawn `python -X importtime -c "import ailsa.cli.main"`-style subprocess and assert `rdkit`, `scipy`,
`nmrglue` not in `sys.modules` after resolving `run note --help`; time budget test `ailsa run note` < 1 s (generous
CI margin 2 s). Existing tests that import `from ailsa import X` must keep passing (run `tests/test_cli_main.py`,
`tests/test_skill_lite.py` and a handful of CLI tests on the dev host; the full suite on Sheldon).
**Warning signs:** hook latency > 150 ms; `ailsa run note` > 1 s.

### Pitfall 2: Frontier skill sessions get noisier
**What goes wrong:** a user-level hook install and an always-on "no active run" warning change what the unchanged
frontier skill sees (stderr merged into Bash results, JSON parsed by agents). The paper skill claims "a new run is a
different configuration" are a spec risk (SPEC §12).
**How to avoid:** hooks no-op without a resolvable run; warning gated (Pattern 3); test that a command run with no
env, no pointer and `CLAUDECODE=1` prints nothing extra and that stdout is byte-identical to before for `--format json`.

### Pitfall 3: Mid-session `/clear` or resume changes the session id
**What goes wrong:** the pointer `<ws>/.sessions/<id>` no longer matches; hooks and tools lose the run.
**How to avoid:** `SessionStart` hook with `source` in `clear|resume|fork` re-binds only if `AILSA_RUN_DIR` is set;
otherwise the lean skill's step 0 is re-run by the agent (init is idempotent per session); render "binding lost at
seq N" when events stop. Compaction keeps the id (no action).

### Pitfall 4: Contract test blocks the new commands
See "Lean skill wiring": `test_same_tools_as_frontier_skill` rejects any command the frontier skill lacks; use an
explicit, commented allow-list. The 20 000-token and 200-line limits also bind.

### Pitfall 5: Remote PATH and binary-name case
Non-interactive ssh has no `~/.local/bin` on Sheldon; the binary is `lsd` there and `LSD` on the Mac (case-insensitive
filesystem hides the difference locally). `bash -lc`, try both names, allow config override; test the resolver with a
fake `ssh` shim on `PATH` (no network in CI).

### Pitfall 6: Hook payload fields vary by version and mode
`Notification` may not fire in `-p`; `SessionEnd` is not documented for `-p`; `tool_response` shapes vary per tool; the
`UserPromptSubmit` prompt arrives with `<pasted_content>` wrappers. Parse defensively (`.get`), store unknown payloads
as `raw_keys`, record `claude_version` from the launcher, and render absent hook categories as "not recorded by this
harness" only when **no** hook-origin event exists in the run (a zero count with hooks active is a real zero).

### Pitfall 7: Agent files outside `agent/` (D-08)
`finalize` scans the run folder (no symlink following; `os.walk(followlinks=False)`) for files not registered in the
artefact index and not under `agent/`, `transcript/`, `renderings/`; lists them as warnings and renders them
"unverified". It must not read file contents that are unregistered artefacts into the rendering.

### Pitfall 8: Race and orphan hygiene
Parallel benchmark runs share one workspace: workspace-level lock for check-and-create (D-04), unique run folder via
`mkdir` exclusive with retry on the 4-character suffix. The launcher must wait on its child and not leave detached
helpers; the optional background view export is a single child that exits by itself; check `pgrep -fl` after every
local test run (user lesson on orphaned pool workers).

### Pitfall 9: Post-run writes (REC-23)
After `run.finished` the writer refuses everything except (a) hook-origin `session.ended`/`transcript.copied`/
`agent.stopped` events flagged `after_finish: true` and (b) `annotation.added` with `post_run: true`. Without this the
Stop/SessionEnd hooks of the finishing session would either be lost or break REC-23.

### Pitfall 10: Blind mode leaks through the record itself
`prompt.submitted` stores the verbatim invocation prompt (REC-09), which may contain the formula or a path; the run
folder name in blind mode uses only the dataset folder name; manifest `dataset.label` is governed by blind mode; the
inventory never reads titles; `identity.derived` is flagged hidden-in-blind; do not log environment variables wholesale
in `tool.invoked` (could contain tokens).

### Chain verification

```python
import hashlib, json
def verify(path, run_id):
    prev = hashlib.sha256(run_id.encode()).hexdigest(); bad = None; n = 0
    with open(path, "rb") as fh:
        for raw in fh:
            body = raw.rstrip(b"\n")
            try: ev = json.loads(body)
            except ValueError: return {"clean": False, "first_bad": n + 1, "reason": "unparseable_or_truncated"}
            n += 1
            if ev.get("seq") != n or ev.get("prev") != prev:
                return {"clean": False, "first_bad": n, "reason": "chain_break"}
            prev = hashlib.sha256(body).hexdigest()
    return {"clean": True, "events": n, "head": prev}
```
// A `log.recovered` event legitimately carries `prev` = hash of the discarded partial bytes; the verifier treats it as
"incomplete from here (crash recovered)", not as tampering.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Command injection through hook payload text (prompts, commands) | Tampering / Elevation | exec-form hooks; payload is data, never concatenated into a shell string |
| ssh option injection via alias (`-oProxyCommand=…`) | Elevation | regex-validate alias, `--` before host, `shlex.quote` for the remote script |
| Path traversal via `DEFF` filenames or artefact paths when staging/copying | Tampering / Info disclosure | basename-only, resolve and check containment, refuse symlinks |
| Symlink planted in `agent/` pointing outside (scanned or copied by `finalize`/transcript copy) | Info disclosure | `followlinks=False`, `lstat`, copy only regular files within size caps |
| Blind leak through workspace readability, prompts in events, folder names | Info disclosure | blind folder name rule, prior-run refusal, `prior_runs_readable` flag, no title reads |
| Log tampering or silent truncation | Tampering / Repudiation | hash chain, `chain_head` stored twice, verify command, D-09 marking |
| Confidential run sends data to web tools | Info disclosure | `--disallowedTools WebFetch WebSearch` for class confidential; record whether enabled |
| Markdown injection from agent text into renderings | Tampering | renderer escapes agent-supplied text in tables/links; HTML-safe handling is a viewer concern (SEC-09, later) |
